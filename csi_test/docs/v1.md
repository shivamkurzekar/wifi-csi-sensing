# csi_test — v1: CSI capture, analysis, and plotting

**Commit:** `b4a2929` — "Add CSI capture firmware and host-side analysis tooling"
**Target:** ESP32-S3, ESP-IDF v5.4
**Status:** working end-to-end (firmware → CSV → analysis → HTML report), verified on real hardware

This doc explains what the project does, how the pieces fit together, and how
to reproduce the whole pipeline. Written so another engineer can pick this up
without having sat through the debugging session that produced it.

---

## 1. What this project is

`csi_test` is ESP32-S3 firmware that captures **WiFi Channel State Information
(CSI)** — the per-subcarrier amplitude/phase distortion the WiFi radio
measures on every received packet, as a side effect of normal OFDM decoding.
CSI is sensitive to the physical environment (walls, furniture, moving
bodies), which is why it's commonly used for WiFi-based sensing (motion /
presence detection) even though the chip's actual reason for computing it is
just to equalize the signal for demodulation.

The firmware streams CSI data out over serial as CSV. A small set of Python
tools on the host side turn that into an interactive HTML report so the data
is actually inspectable, not just a wall of numbers.

```
ESP32-S3 (WiFi STA, CSI capture)
        │  CSV over serial ("CSI,<ts>,<rssi>,<channel>,<n>,amp0,phase0,...")
        ▼
tools/capture_csi.py     — records serial → CSV, tagged with host wall-clock time
        │
        ▼
tools/analyze_csi.py     — CSV → per-subcarrier amplitude matrix + variability score → JSON
        │
        ▼
tools/build_report.py    — JSON + tools/report_template.html → self-contained HTML report
```

## 2. What we've done so far (v1)

1. Got baseline CSI capture working on an ESP32-S3, connecting to WiFi as a
   station.
2. Fixed a startup crash: `esp_wifi_set_csi_config()` was returning
   `ESP_FAIL` because `CONFIG_ESP_WIFI_CSI_ENABLED` was not set in
   `sdkconfig` — CSI has to be enabled at build/menuconfig time, not just
   called from code. Now enabled.
3. Rewrote the CSI callback to compute and print **amplitude + phase per
   subcarrier** as a CSV line, instead of a raw hex dump of the first 32
   bytes.
4. Hit and fixed a **task watchdog crash**: the callback runs inside the
   high-priority WiFi driver task, and printing ~192 floats over UART on
   every packet was slow enough (~200ms per line at 115200 baud) to starve
   the idle task and trip the watchdog. Fixed by decoupling: the callback now
   only `memcpy`s the raw packet into a queue and returns immediately; a
   separate low-priority task does the amplitude/phase math and printing.
   See §4.
5. Moved the WiFi password out of source into a gitignored header
   (`main/wifi_credentials.h`), with `main/wifi_credentials.h.example` as the
   checked-in template.
6. Built host-side tooling to record, analyze, and visualize a capture
   (`tools/`).
7. Ran a real 45-second test capture (steady ~10 pkt/s via a background
   `ping` to the ESP32) and visually confirmed the pipeline picks up real
   physical events: a quiet baseline period, a period of elevated CSI
   variability (movement near the signal path), and a sharp RSSI drop
   (something physically blocking the line of sight between the ESP32 and
   the router).

## 4. Firmware architecture (`main/csi_test.c`)

### 4.1 CSI configuration

```c
wifi_csi_config_t csi_config = {
    .lltf_en = true,           // legacy long training field — present in every 802.11 packet
    .htltf_en = true,          // HT (802.11n) long training field — only in HT packets
    .stbc_htltf2_en = true,    // 2nd HT-LTF used for STBC (space-time block code) packets
    .ltf_merge_en = true,      // average LLTF + HT-LTF into one estimate when both exist
    .channel_filter_en = false,// off = keep each subcarrier independent, no smoothing
    .manu_scale = false,       // false = let the hardware auto-scale the CSI values
    .shift = false,            // unused since manu_scale is false
};
```

This captures CSI from every training field type the radio can extract it
from, keeps subcarriers unsmoothed (more detail, more noise), and lets the
hardware auto-scale. Because all three LTF types are enabled, a single
packet's CSI buffer is actually **three concatenated groups** (legacy,
HT-LTF, STBC-HT-LTF2), each roughly 64 subcarriers wide — this is why
`num_subcarriers` in the captured data is ~192 for HT packets, not ~64.

### 4.2 Why the callback doesn't do any printing

`esp_wifi_set_csi_rx_cb()` registers a callback that runs **inside the WiFi
driver's own task**, which runs at high priority. Early versions of this
firmware called `printf()` directly from that callback to emit the CSV line.
At ~192 subcarriers × 2 floats, one line is ~2.5KB — at 115200 baud that's
roughly 200ms to transmit, back-to-back with packets arriving every ~200ms.
The WiFi task stayed busy nonstop, starved the idle task, and the task
watchdog fired (`Task watchdog got triggered`), aborting the device.

**Fix — never do slow work in the callback.** The callback now just copies
the raw bytes into a fixed-size struct and pushes it onto a FreeRTOS queue
with a non-blocking send (drops the sample if the queue is full, rather than
ever blocking):

```c
static void wifi_csi_cb(void *ctx, wifi_csi_info_t *data) {
    ...
    memcpy(record.buf, data->buf, record.len);
    if (xQueueSend(csi_queue, &record, 0) != pdTRUE) {
        dropped_count++;
    }
}
```

A separate task (`csi_print_task`, priority 3 — above idle, well below the
WiFi task) pulls records off the queue and does the actual amplitude/phase
computation and `printf`, off the WiFi task's critical path.

### 4.3 Turning raw bytes into amplitude/phase

CSI data (`wifi_csi_info_t.buf`) is a sequence of **signed 8-bit
`(imaginary, real)` pairs, one pair per subcarrier**. If
`first_word_invalid` is set, the first 4 bytes (first 2 subcarriers) are
hardware garbage and are skipped.

```c
int start = record.first_word_invalid ? 4 : 0;
int num_subcarriers = (record.len - start) / 2;

for (int i = 0; i < num_subcarriers; i++) {
    int idx = start + (i * 2);
    float im = (float)record.buf[idx];
    float re = (float)record.buf[idx + 1];
    float amplitude = sqrtf((im * im) + (re * re));
    float phase = atan2f(im, re);
    ...
}
```

## 5. What values we're actually capturing

Per received packet, `wifi_csi_info_t` gives us (see
`esp_wifi_types_native.h` in ESP-IDF):

- `rx_ctrl.rssi` — received signal strength, dBm
- `rx_ctrl.channel` — WiFi channel the packet was received on
- `rx_ctrl` also carries rate/MCS, noise floor, STBC flag, timestamp, etc.
  (not all currently logged — available if needed later)
- `mac` / `dmac` — source/destination MAC of the packet the CSI came from
- `buf` / `len` — the CSI payload itself: `(imaginary, real)` byte pairs, one
  per subcarrier (see §4.3)
- `first_word_invalid` — whether the first 4 bytes of `buf` are garbage

From this we compute **amplitude** (`sqrt(im² + re²)`, signal strength per
subcarrier) and **phase** (`atan2(im, re)`, phase shift per subcarrier).

### CSV wire format (over serial, and in `capture_csi.py` output)

```
CSI,<timestamp_us>,<rssi>,<channel>,<num_subcarriers>,amp0,phase0,amp1,phase1,...
```

- `timestamp_us` — ESP32's own clock, microseconds since boot (`esp_timer_get_time()`)
- Every other line on serial is normal ESP-IDF log output (boot logs, WiFi
  driver logs). The `CSI,` prefix is how host tooling picks out the lines
  that matter.

`capture_csi.py` adds one more column when saving to disk: `host_time`, the
recording machine's wall-clock time for that row, so you can correlate "I
walked past it at 14:32:10" with the data afterward.

## 6. How we analyze the values (`tools/analyze_csi.py`)

Input: the CSV from `capture_csi.py`. Output: a compact JSON summary.

1. **Parse and validate.** Each row's `values` column is split into
   `amplitude, phase` pairs. Malformed rows (e.g. a firmware log line that
   got interleaved into a CSV row — see the watchdog issue in §4.2, now
   fixed) are skipped rather than aborting the batch.
2. **Filter to a consistent subcarrier count.** Not every received packet is
   the same shape — e.g. ACK/non-HT frames only carry ~64 subcarriers
   (legacy LTF only) vs ~192 for HT data frames (legacy + HT-LTF +
   STBC-HT-LTF2, see §4.1). We keep only the most common count (`statistics.mode`)
   so the amplitude matrix is rectangular; everything else is dropped from
   this analysis (still present in the raw CSV).
3. **Build the amplitude matrix** — one row per packet, one column per
   subcarrier.
4. **Compute a per-packet variability score** — the population standard
   deviation of amplitude across all "active" subcarriers (columns that
   aren't just null/guard-band zero across the whole capture) in that
   packet. This is the number that spikes when the RF path is disturbed —
   it's the simplest useful signal for "did something change," without
   needing to know which specific subcarrier matters.

Output JSON: `num_packets`, `num_subcarriers`, `duration_s`, `time_s[]`
(seconds since first packet), `rssi[]`, `variability[]`, and the full
`matrix[][]` of amplitudes.

## 7. How we plot it (`tools/build_report.py` + `tools/report_template.html`)

`build_report.py` just embeds the JSON summary into
`report_template.html`'s `__DATA_JSON__` placeholder, producing one
self-contained HTML file — no build step, no server, no external libraries.
Open it directly in a browser.

The report has three views, all built from the same JSON:

1. **Amplitude heatmap** (`<canvas>`) — time on the x-axis (one column per
   packet), subcarrier index on the y-axis, color = amplitude. Color scale
   is a single-hue sequential ramp (light → dark blue), domain clamped to
   the **95th percentile** of amplitude so the handful of very bright pilot
   subcarriers don't wash out the color range for ordinary data. Hovering
   shows exact time / subcarrier / amplitude.
2. **RSSI over time** and **CSI variability over time** (SVG line charts) —
   each is a single series (one hue, no legend needed), with a crosshair +
   tooltip on hover, snapping to the nearest actual sample. Lines break
   visually across gaps > 1.5s in the data rather than interpolating through
   them.
3. **Auto-detected bands** — both line charts shade any period where the
   value strayed more than ~2 standard deviations from the *first 15
   seconds* of the capture (treated as a baseline). This is a purely
   data-driven heuristic, not a ground-truth event marker — it's meant to
   point you at "something happened here," which you then cross-check
   against what you actually did during capture.
4. A collapsible **raw data table** (time / RSSI / variability per packet)
   for anyone who wants the numbers directly instead of the chart.

## 8. How to reproduce a full run

```bash
cd projects/csi_test
source ~/Projects/esp/esp-idf/export.sh

# 1. flash + get the ESP32's IP (printed on connect)
idf.py -p /dev/ttyACM0 flash monitor
# Ctrl+] to exit once you see "Got IP: ..."

# 2. from another device on the same WiFi, keep packets flowing:
#      ping -i 0.1 <esp32-ip>

# 3. record a session
python3 tools/capture_csi.py --port /dev/ttyACM0 --out tools/output/session.csv
# Ctrl+C to stop

# 4. analyze + plot
python3 tools/analyze_csi.py --in tools/output/session.csv --out tools/output/summary.json
python3 tools/build_report.py --summary tools/output/summary.json --out tools/output/report.html
# open tools/output/report.html in a browser
```

`tools/output/` is gitignored — captures are per-session and not checked in.

## 9. Known limitations / v2 candidates

- No ground-truth event markers. The capture script logs host wall-clock
  time per row, but there's no in-band way to mark "movement started here" —
  right now that's done by eyeballing the auto-detected bands against memory
  of what happened during capture. A simple stdin marker (press Enter to tag
  the current moment) would remove the guesswork.
- ~1/3 of captured packets in our test run were non-HT (64 subcarriers) and
  get dropped by the analysis step entirely. Worth deciding whether those
  are useful (they're at least valid RSSI/timing samples) or safe to ignore.
- Only `rssi` and `channel` are pulled out of `rx_ctrl` currently; MCS, STBC
  flag, and noise floor are available and unused.
- Single AP, single ESP32. No multi-node / multi-antenna comparison yet.
