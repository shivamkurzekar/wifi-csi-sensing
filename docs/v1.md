# csi_presence — v1: room presence detection from WiFi CSI

**Target:** ESP32-S3, ESP-IDF v5.4
**Status:** builds clean; not yet flashed/validated on hardware
**Relationship to `csi_test`:** a separate, standalone project. Reuses two
pieces of proven infrastructure from there (see below) but shares no files
and was built without modifying it.

---

## What this is

`csi_test` answers "what does WiFi CSI look like." This project answers a
narrower question: **is there a person in the room, right now, yes or no.**

It streams a live `PRESENCE,...` line over serial on every processed packet
with a motion-energy score and a boolean presence flag — no offline
analysis step required.

## Where the algorithm came from

The core idea — variance of one subcarrier's phase, over time, as a motion
signal, with a self-calibrating ambient baseline and hysteresis to avoid
flicker — is adapted from the *approach* used in
[`ruvnet/RuView`](https://github.com/ruvnet/RuView)'s
`firmware/esp32-csi-node/main/edge_processing.c` (MIT licensed). That
project has real, documented credibility baggage (see its own `PROOF.md`
and the public "AI slop" controversy around it) — but this specific piece
of code was verified by reading it directly, and it's a genuinely sound,
standard signal-processing technique independent of anything else in that
project. Nothing was copied verbatim; this is a fresh implementation, with
one deliberate change from the source approach (below).

## Why this is a better signal than what `csi_test`'s report computes

`csi_test`'s "variability" metric is the spread of amplitude **across all
subcarriers within one packet** — a spatial snapshot. A room that's simply
furniture-dense and RF-complex can score "high variability" even with
nobody moving, because the metric never looks at *time*.

This project's "motion energy" is the variance of **one subcarrier's phase
over the last ~1 second** — it only responds to the channel actually
*changing*, which is what motion causes (new multipath, signal blocked/
unblocked) and a static-but-complex room does not.

## Algorithm

1. **Extract + unwrap phase** for every subcarrier, every packet. Unwrapping
   matters: raw `atan2` wraps at ±π, so a real ~3.2 rad phase change would
   otherwise look like a fake jump from +3.1 to -3.1. (`csi_test` does not
   do this — a gap noted in its own docs.)
2. **Pick the noisiest subcarrier** via a running (Welford) variance
   tracker across all subcarriers, re-evaluated every 100 processed frames.
3. **Track only that subcarrier's phase** into a ring buffer.
4. **Motion energy** = variance of the last 20 samples in that buffer.
5. **Adaptive calibration**: watch ambient motion energy with the room
   (presumed) empty, then set `threshold = ambient_mean + 3 × ambient_stddev`.
6. **Hysteresis + debounce** (a Schmitt trigger): enter "present" the
   instant the score crosses the threshold; only clear "present" after 5
   consecutive frames below half the threshold, so a score dithering near
   the boundary doesn't flicker the flag.

## The one deliberate change from the source approach

RuView calibrates over a **fixed frame count** (1,200 frames), implicitly
assuming a steady ~20 Hz capture rate. Our own earlier capture on this
exact network showed wildly irregular inter-packet gaps (0.2s to 2.6s,
depending on ambient traffic) — so a frame-count calibration window would
take an unpredictable amount of wall-clock time, or worse, calibrate
against a burst of only a few seconds' worth of samples.

This project calibrates over a **fixed 60 seconds of wall-clock time**
(`CALIB_SECONDS`, using the ESP32's own timestamp), regardless of how many
packets actually arrived in that window — the window's *meaning* (60s of
ambient observation) holds regardless of traffic rate. If too few samples
arrive in that window (`CALIB_MIN_SAMPLES`), it keeps waiting rather than
committing to a threshold estimated from noise.

## Known limitations (v1)

- **Not yet validated on hardware.** Builds clean; hasn't been flashed or
  tested against a real empty-room / occupied-room comparison yet.
- **Mixed packet shapes.** Like `csi_test`, some received packets carry
  fewer subcarriers than others (e.g. non-HT frames vs. HT frames — see
  `csi_test/docs/v1.md` §6). When the subcarrier count changes between
  packets, phase-unwrap continuity is deliberately dropped for that one
  frame rather than unwrapping across a discontinuity that isn't real
  motion. This causes a one-frame gap in the phase history whenever packet
  type switches.
- **Heuristic, not validated accuracy.** Same caveat RuView's own docs
  carry: this is a threshold-crossing heuristic, not something with a
  measured false-positive/false-negative rate. Strong RF interference can
  plausibly trigger false positives.
- **Single subcarrier.** Only the single noisiest subcarrier feeds the
  motion score; a person standing very still in a spot that happens to
  barely perturb that one subcarrier could be missed even while other
  subcarriers show more signal. A future version could combine top-K
  subcarriers instead of just the top-1.
- **`WIFI_SSID` / `WIFI_PASSWORD`** live in `main/wifi_credentials.h`
  (gitignored) — same pattern as `csi_test`, see its
  `main/wifi_credentials.h.example`.

## How to test it

```bash
cd projects/csi_presence
source ~/Projects/esp/esp-idf/export.sh
idf.py -p /dev/ttyACM0 flash monitor
```

Keep the room empty for the first 60 seconds (calibration window — the boot
log says so). After that, watch the last column of each `PRESENCE,...` line
flip to `1` when someone walks in.

```
PRESENCE,<timestamp_us>,<rssi>,<primary_subcarrier_idx>,<motion_energy>,<threshold>,<calibrated>,<present>
```
