# analyse_csi — v1: signal-study tool with a live browser viewer

**Target:** ESP32-S3, ESP-IDF v5.4
**Status:** working end-to-end, verified on real hardware
**Relationship to `csi_test` / `csi_presence`:** a third, standalone project
in the same family. Shares no files with either, neither was modified while
building this. Reuses two pieces of infrastructure already proven out there
(the `CONFIG_ESP_WIFI_CSI_ENABLED` sdkconfig fix, and the queue +
low-priority-task split) -- see `csi_test/docs/v1.md` §4 for why those exist.

---

## 1. What this project is, and how it's different from the other two

`csi_test` answers "what does CSI look like" (offline, via a generated
report). `csi_presence` answers "is there a person in the room" (a specific
detection heuristic). **`analyse_csi` answers neither** -- it's a
general-purpose signal-study tool: capture CSI as cleanly and cheaply as
possible, do zero analysis on the device, and let you watch it live in a
browser while deciding what's actually worth measuring.

The defining design choice: **the ESP32 does no signal math at all.** It
doesn't compute amplitude, doesn't compute phase, doesn't even format
numbers as text -- it just forwards the raw CSI bytes over serial as
compactly as possible. All analysis (amplitude, phase, whatever you want to
try next) happens in Python, on the host, so it can change without ever
reflashing the board.

## 2. Architecture

```
ESP32-S3 (main/analyse_csi.c)
  wifi_csi_cb (WiFi driver task, high priority)
      -> memcpy raw CSI bytes into a FreeRTOS queue, return immediately
  csi_stream_task (priority 3, off the WiFi task's critical path)
      -> pack a binary frame (magic + header + raw payload + checksum)
      -> write raw bytes to stdout (the same stream as ESP-IDF's text logs)
        |
        | USB serial
        v
tools/proto.py           -- FrameReader: scans for the magic word, validates
                             checksum, resyncs byte-by-byte on failure
tools/server.py           -- background thread decodes frames continuously;
                              HTTP server (stdlib only) answers /data.json polls;
                              every frame is also logged to a timestamped CSV
tools/live_view.html      -- polls /data.json ~1x/second, draws the waterfall
                              and four line charts (see §5)
```

### 2.1 The binary wire protocol

Full authoritative spec: `main/csi_wire_protocol.h`. Summary:

```
offset  size  field
0       4     magic (0xC5, 0x10, 0xAC, 0x02)
4       8     device_us   (uint64 LE) -- esp_timer_get_time() at capture
12      1     rssi        (int8)
13      1     channel     (uint8)
14      1     first_word_invalid (0 or 1)
15      2     payload_len (uint16 LE)
17      N     payload     -- raw bytes, exactly wifi_csi_info_t.buf
17+N    2     checksum    (uint16 LE) -- additive sum mod 65536 of
                           everything from offset 4 through the end of payload
```

Frames share the serial link with ESP-IDF's own text logs (boot messages,
WiFi driver logs), so a log line can land in between two frames, or even
happen to contain 4 bytes that coincidentally match the magic word. The
decoder (`tools/proto.py`) handles this as normal operation, not corruption:
scan for the magic word, validate the checksum, and if it fails, slide
forward one byte and keep scanning. This is covered by unit tests for three
cases: interleaved log text, a deliberately corrupted frame, and
byte-at-a-time feeding (worst-case serial chunking) -- see the tests
embedded in the commit history if you want to rerun them.

### 2.2 Why binary instead of CSV (`csi_test`'s approach)

Formatting ~192 subcarriers as ASCII floats is expensive in both bytes and
CPU time -- it's the reason `csi_test` needed the queue/task split in the
first place just to avoid starving the watchdog. This project avoids the
cost entirely rather than just tolerating it: raw bytes, no `sqrt`/`atan2`/
`printf` on-device at all.

## 3. A real hardware bug found and fixed here

ESP-IDF's console VFS translates outgoing `\n` (0x0A) to `\r\n` by default,
for terminal compatibility. Fine for text logs; fatal for a binary protocol,
since 0x0A appears constantly in raw CSI payload bytes (they span the full
signed-byte range). **First test result: 0/12 frames decoded, resync_count
climbing to 10.** Root-caused by inspecting the raw bytes directly -- found
a `0d 0a` pair sitting where a single `0x0A` payload byte should have been.

Fix: disable TX line-ending translation on both console backends at boot
(this build has both UART and USB-Serial-JTAG consoles enabled in sdkconfig,
so both are disabled rather than assuming which one is actually active):

```c
uart_vfs_dev_port_set_tx_line_endings(UART_NUM_0, ESP_LINE_ENDINGS_LF);
usb_serial_jtag_vfs_set_tx_line_endings(ESP_LINE_ENDINGS_LF);
```

After the fix: 12/12 frames decoded, 0 resyncs, real data. See
`main/analyse_csi.c`'s `app_main()` for the comment with the full story.

## 4. What values you're actually working with

Per subcarrier, per packet: **two raw signed bytes**, `im` and `re`
(-128 to 127 each). That's the entire raw measurement. Everything else is
derived:

```python
amplitude = sqrt(im^2 + re^2)   # math.hypot(im, re)
phase     = atan2(im, re)        # -pi to +pi
```

A real worked example (from `docs/data/raw50-capture-summary.md`, packet 0,
subcarrier 1): raw bytes `im=-1, re=-24` give `amplitude=24.02`,
`phase=-3.100 rad`. See that doc for the full derivation and a 50-packet
real dataset (`docs/data/raw50_subcarriers.csv`, 9,600 rows) answering two
structural questions directly from real captures:

- **Is subcarrier count always the same per packet? No** -- it depends on
  whether the received packet was HT (this config: ~192 subcarriers) or
  non-HT/legacy (~64). Both shapes occur in normal traffic.
- **Does subcarrier index k mean the same physical subcarrier across
  packets? Yes, within the same packet shape** (fixed buffer layout set by
  the driver); **not confirmed across different shapes** -- treated as an
  open risk, matching how `csi_presence` handles the same situation.

**Important finding from that same dataset**, worth reading in full in
`docs/data/raw50-capture-summary.md`: raw *phase*, tracked for one
subcarrier across 50 real packets, looks dominated by per-packet timing/
frequency offset rather than physical motion (amplitude stayed tight and
stable over the same packets; phase scattered near-uniformly across the
entire range). This is a plausible explanation for why `csi_presence`'s
calibrated threshold came out so much higher than any real motion measured
during its walk-test -- flagged as a hypothesis to investigate, not a
proven fact.

## 5. What's plotted, and how it works

| Chart | Data source | Window |
|---|---|---|
| **Live waterfall** | amplitude, all subcarriers | last `RECENT_WINDOW` = 300 packets, scrolling |
| **Phase waterfall** | raw phase, all subcarriers | same 300-packet window |
| **RSSI -- recent** | `rx_ctrl.rssi` (not derived from subcarriers at all) | same 300-packet window |
| **Variability -- recent** | population std-dev of amplitude across non-zero subcarriers, one number per packet | same 300-packet window |
| **RSSI -- whole session** | same RSSI value | every packet since session start (capped at `HISTORY_CAP` = 20,000, oldest 10% dropped if exceeded) |
| **Variability -- whole session** | same variability metric | whole session, same cap |

The amplitude waterfall is a classic SDR-style "waterfall" display: each
column is one packet (newest on the right), each row a subcarrier, color =
amplitude (clamped to the 95th percentile of whatever's currently visible,
so a few bright pilot subcarriers don't wash out the rest of the scale --
this also means color is relative to the current window, not an absolute
physical mapping). Both waterfalls share axes: subcarrier index on the
left, real clock time along the bottom -- but note the X axis is
packet-sequence-based, not a linear time scale: each column is one packet,
evenly spaced regardless of the real gap to the packet before it, so bursty
traffic visually compresses time and sparse traffic stretches it. All five
charts share the same `session_start_iso` reference and `formatClockTime`
helper, so times are comparable across all of them.

**The phase waterfall** uses the same column/row layout but a *hue wheel*
instead of a light-to-dark ramp, because phase is circular (-pi and +pi are
the same physical angle) -- a sequential ramp would make the wrap-around
point look like two opposite extremes. Added specifically to let the
finding above be watched directly: expect it to look like largely
uncorrelated color noise, column to column, until a calibration step exists
to remove the per-packet timing/frequency offset. It is not a validated
signal yet -- it's a diagnostic view, added on purpose while that offset
issue is still open.

## 6. How to run it

```bash
cd projects/analyse_csi
source ~/Projects/esp/esp-idf/export.sh

# only needed the first time, or after a firmware change:
cp main/wifi_credentials.h.example main/wifi_credentials.h   # fill in your SSID/password
idf.py -p /dev/ttyACM0 flash

cd tools
python3 server.py --port /dev/ttyACM0 --http-port 8000
```

It prints a URL (e.g. `http://192.168.0.113:8000`) -- open that from any
browser on the same WiFi, including your phone.

**You need continuous traffic for a smooth live view.** Ambient WiFi
traffic alone is sparse and irregular (gaps of multiple seconds are normal).
From another device on the same network:

```bash
ping -i 0.1 <esp32-ip>
```

### 6.1 Finding the ESP32's current IP

The IP can change between boots (normal DHCP behavior) -- it is **not**
guaranteed to stay the same as your last session. If `server.py` reports
zero frames despite a supposedly-continuous ping, the most likely cause is
the ping target is stale. To find the current IP, reset the board and watch
for the one-time boot log line:

```bash
python3 -c "
import serial, time
ser = serial.Serial('/dev/ttyACM0', 115200, timeout=1)
ser.dtr = False; ser.rts = True; time.sleep(0.1); ser.rts = False; time.sleep(0.1)
data = b''
end = time.time() + 6
while time.time() < end:
    data += ser.read(500)
ser.close()
import re
m = re.search(rb'Got IP: (\d+\.\d+\.\d+\.\d+)', data)
print(m.group(1).decode() if m else 'not found, try again')
"
```

This toggles RTS/DTR the same way `idf.py monitor`/`esptool` do to trigger a
board reset, then captures the fresh boot log.

### 6.2 Serial port conflicts

Only one process can hold `/dev/ttyACM0` at a time. If you see:

```
serial.serialutil.SerialException: device reports readiness to read but
returned no data (device disconnected or multiple access on port?)
```

check for a leftover `server.py` (or any other script) still holding the
port before starting a new one:

```bash
ps aux | grep server.py
fuser /dev/ttyACM0
```

### 6.3 If the device seems alive on WiFi but sends nothing over serial

This happened once during development: the board responded to ping
normally but produced zero bytes over serial for an extended period, with
unusually high ping latency (~600-700ms, vs. a normal few ms) just before
it stopped. A board reset (§6.1's script) resolved it and the device
resumed streaming normally afterward, but the reset also produced a new
DHCP-assigned IP -- so a hang like this is also a good reason to re-check
the IP before assuming your ping target is still correct.

## 7. Known open items

- **Phase is plotted but not calibrated.** The phase waterfall (added
  after §4's finding) shows raw phase as-is -- expected to look like
  mostly uncorrelated noise until a phase-calibration pass exists (e.g. a
  linear-fit correction across subcarriers within one packet, to remove
  the per-packet timing/frequency offset before phase becomes trustworthy
  to read). It's a diagnostic view of the open problem, not a solution to
  it.
- **Mixed packet shapes** aren't filtered or normalized anywhere in this
  project (unlike `csi_test`'s `analyze_csi.py`, which filters to the modal
  subcarrier count). The waterfall just draws whatever each packet reports,
  up to `MAX_SUBCARRIERS` = 256 columns of headroom.
- **No automatic reconnect handling** in `server.py` if the board reboots
  mid-session -- the serial connection itself survives a board-side reset
  fine (proven during the investigation in §6.3), but if the IP changes,
  anyone pinging the old address won't notice until told.
- **Session CSV logs are not rotated or size-limited.** A very long session
  will produce a large file in `tools/data/` (gitignored).
